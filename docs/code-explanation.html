Spring AI Demo 代码讲解

按照「一个请求是怎么一层层流动的」来读，8 个 Java 类，职责单一、非常清晰。

JDK 25 Spring Boot 4.1.1 Spring AI 2.0.1 火山方舟 glm-5.3 Function Calling

1整体架构

浏览器  static/index.html （4 个标签页）
▼  HTTP / SSE
Controller 层
ChatController（对话/流式/结构化） · ToolController（工具）
▼
ChatClient（统一门面）
经过 Advisor 链：MessageChatMemoryAdvisor（记忆拦截器）
▼  HTTPS（OpenAI 官方 SDK）
火山方舟大模型  glm-5.3

旁边还有两个配角：@Tool 本地方法 天气 / 时间 / 计算器， 以及 WeatherService 调真实天气 API。模型回答不了的事（查实时天气、算数），就「反过来调用」它们。

① Controller 层 — 接收 HTTP 请求、返回 JSON/文本/流
② ChatClient — Spring AI 的统一调用门面，拼装 提示词/记忆/工具
③ Advisor — 套在模型调用外的拦截器（这里负责多轮记忆）
④ OpenAI SDK — 真正发 HTTP 给火山方舟
⑤ Tools — 模型可调用的本地 Java 能力

3核心配置 config/ChatConfig.java

这里装配了整个 Demo 的「大脑」——ChatClient，定义了两个 Bean。

① 对话记忆 ChatMemory

@Bean
public ChatMemory chatMemory() {
    return MessageWindowChatMemory.builder()
            .maxMessages(20)   // 每个会话只保留最近 20 条（滑动窗口）
            .build();
}
  • 底层默认是 InMemoryChatMemoryRepository，本质是 JVM 堆里的一个 Map<会话id, List<消息>>；
  • 重启即清空，多实例不共享；要持久化可换 JdbcChatMemoryRepository / Redis。

② ChatClient

@Bean
public ChatClient chatClient(ChatClient.Builder builder, ChatMemory chatMemory) {
    return builder
        .defaultSystem("你是一个乐于助人的中文 AI 助手，回答简洁、准确、有条理。") // 人设
        .defaultAdvisors(MessageChatMemoryAdvisor.builder(chatMemory).build()) // 记忆拦截器
        .build();
}
ChatClient.Builder 由 starter 依据 application.yml 自动配好（已含 Key、base-url、模型）， 这里只追加「系统人设 + 记忆 Advisor」。
MessageChatMemoryAdvisor 的作用：调用模型前按 conversationId 取出历史塞进请求； 拿到回答后把本轮对话存回。模型本身无状态，记忆全靠它。

4三大对话接口 controller/ChatController.java

构造器注入全局唯一的 ChatClient 单例。

A. 普通多轮对话  GET /chat

return chatClient.prompt()                       // 开始构建一次请求
        .user(message)                    // 用户输入
        .advisors(a -> a.param(ChatMemory.CONVERSATION_ID, conversationId))
        .call()                            // 同步阻塞调用
        .content();                        // 取回答的纯文本

.advisors(...param...) 不是存数据，而是告诉记忆拦截器「这次请求属于哪个会话」。不同 conversationId 互相隔离。

B. 流式输出  GET /chat/stream

return chatClient.prompt()...
        .stream()      // 边生成边推送，返回 Reactor 的 Flux<String>
        .content();    // Spring MVC 自动按 SSE 一帧帧写出：data: xxx

方法里手动 response.setContentType("text/event-stream;charset=UTF-8")， 是为了修复「直接把接口贴进浏览器地址栏，中文按 GBK 解码而乱码」的问题（真正用 EventSource 消费时本就按 UTF-8）。

C. 结构化输出  GET /chat/actor

return chatClient.prompt()
        .user("列出演员 " + actor + " 出演过的 5 部著名电影。")
        .call()
        .entity(ActorFilms.class);   // ⭐ 模型 JSON 自动转成 Java 对象

Spring AI 会：① 根据 ActorFilms 结构生成 JSON Schema 发给模型；② 模型返回 JSON；③ 自动反序列化成强类型 record。

⚠️ 因为全局挂了记忆 Advisor，它强制要求会话 id，所以 /chat/actor 和工具接口都传了一个固定 conversationId， 否则会抛 conversationId cannot be null。

5结构化 DTO dto/ActorFilms.java

public record ActorFilms(String actor, List<String> films) {}

用 Java record 定义不可变数据对象，字段名就是给模型的 JSON 字段名： {"actor":"周星驰","films":[...]}。

6工具集合 tool/DemoTools.java

这是让模型「长出手脚」的类，是个 @Component，构造注入 WeatherService。 每个能被模型调用的方法都标了 @Tool：

@Tool(name = "getWeather",
      description = "查询指定城市当前的实时天气…输入城市中文名")
public String getWeather(
        @ToolParam(description = "城市中文名，例如：北京") String city) {
    return weatherService.currentWeather(city);
}
description 是灵魂。Spring AI 把「方法名 + 描述 + 参数（反射类型 + @ToolParam 说明）」自动生成一份 JSON Schema 发给模型； 模型据此判断「要不要调、怎么传参」。
工具方法作用触发示例
getWeather(city)真实实时天气（Open-Meteo）北京天气怎么样？
getCurrentTime(tz)当前日期时间，可指定时区现在几点了？
calculator(expr)四则运算（自带安全解析器）(12+8)*3 等于多少

为什么计算器要自己写解析器？

内部是一个递归下降解析器 ExprParser（文法 expr → term → factor）， 而不是用 ScriptEngine / JS 引擎——为的是只能算数学表达式， 杜绝模型传入恶意代码导致任意代码执行。

7调用链记录 tool/ToolTraceHolder.java

private static final ThreadLocal<List<Map<String,Object>>> TRACE = new ThreadLocal<>();

Tomcat 每个请求跑在独立线程上，用 ThreadLocal 存「本次请求触发了哪些工具」天然线程隔离：

Controller 请求开始：begin() 初始化列表
每个 @Tool 方法执行时：record(工具名, 参数, 结果)
Controller：snapshot() 读出调用链返回前端
finally { clear(); } 清理，防止线程池复用串数据 / 内存泄漏

仅用于教学展示调用过程；生产中更推荐用 Spring AI 的 Tool Observation / Advisor 来观测。

8工具接口 controller/ToolController.java

String answer = chatClient.prompt()
        .user(message)
        .tools(tools)          // ⭐ 把 DemoTools 注册给这次请求，模型才看得到 3 个工具
        .advisors(a -> a.param(CONVERSATION_ID, "tool-demo"))
        .call().content();

List<...> calls = ToolTraceHolder.snapshot();
return Map.of("answer", answer, "toolCalls", calls, ...);

和普通对话唯一的区别就是多了 .tools(tools)。返回「最终答案 + 工具调用链」， 前端才能画出 🧑问题 → 🔧工具调用 → 🤖最终回答 的过程。

9真实天气服务 weather/WeatherService.java

独立 @Component，封装免费、免 Key 的 Open-Meteo，分两步：

① geocoding 接口

城市中文名 → 经纬度（用 UriComponentsBuilder 编码中文）

② forecast 接口

经纬度 → 实时天气 JSON（温度/湿度/风/天气码）

用 Jackson 把 JSON 映射成一组 record（@JsonProperty("temperature_2m") 对应下划线字段）， 再用 describeWeather()（WMO 天气码 → 中文）和 windDirection()（角度 → 八方位）拼成中文句子。

HTTP 客户端用 JdkClientHttpRequestFactory（JDK 内置 HttpClient）。

Spring AI 1.x → 2.x 的坑：2.x 改用官方 OpenAI SDK，base-url 必须含完整版本段， 1.x 的 spring.ai.openai.chat.completions-path 在 2.x 已移除（配了不生效）。

11一次工具调用的完整时序（最关键）

以「北京天气怎么样？」为例 —— 一次问答背后通常是 2 次模型请求：

浏览器发来 GET /tool/chat?message=北京天气
ToolController：ThreadLocal.begin()，.tools(demoTools)
经过 MessageChatMemoryAdvisor（取/存历史），组装请求
第 1 次请求模型：发送 [系统提示 + 用户问题 + 3 个工具的 JSON Schema]
模型判断需要天气 → 返回 tool_call: getWeather({"city":"北京"})（此刻还不是最终答案）
Spring AI 框架自动反射执行 DemoTools.getWeather("北京")
└─ WeatherService → Open-Meteo 两次 HTTP → 「北京当前：大部晴朗 21.2℃…」
第 2 次请求模型：框架把工具结果作为 tool 消息回传
模型基于真实数据，生成自然语言最终答案
Controller 用 snapshot() 拿到工具链，组装 {answer, toolCalls} 返回
前端渲染：问题 → 工具调用（参数/返回值）→ 最终回答

12核心知识点 & 踩过的坑

🧩 三大 AI 能力

.call()/.stream() 对话 · .entity() 结构化 · .tools() 工具调用

🧠 无状态模型 + 外部记忆

记忆靠 Advisor + ChatMemory，模型本身不记任何东西

🔒 工具安全

计算器自写解析器不用脚本引擎；天气异常返回友好字符串而非 500

♻️ ThreadLocal 必清

try/finally 里 clear()，避免线程池复用串数据

过程中解决的典型问题

现象原因解决
调用模型 404base-url 被拼成 /api/v3/v1/chat/completions2.x 用完整版本前缀 /api/plan/v3
SSE 中文乱码响应头缺 charset，浏览器按 GBK 解码显式 text/event-stream;charset=UTF-8
天气「未找到城市」RestClient 把已编码的 % 二次编码UriComponentsBuilder 构建参数 + JDK HttpClient

想扩展自己的业务能力？ 照着 DemoTools 加一个带 @Tool 的方法即可 （查数据库、调内部 HTTP API、发邮件……），把方法的 description 写清楚，模型就会在合适时机自动调用。
